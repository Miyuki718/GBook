# 关键代码讲解

## 为什么新增共享包

`packages/core/src/index.ts` 管业务规则，Web 与 MCP 只负责协议适配。两处都调用 saveAnnotation，所以“原文必须匹配”和“修订号不能过期”不会出现两份不同实现。
Drizzle 的参数化 sql 模板会把插值作为参数，不把用户批注拼成 SQL 语句。事务同时保护消息成对创建与备份恢复。

## 批注为什么有 revision

读取时 revision=1；保存时客户端带回 1，服务端确认后改为 2。如果 MCP 已经改到 2，而网页仍拿着 1，就返回冲突，避免悄悄丢掉另一处修改。
定位仍使用 Phase 1 的 UTF-16 算法，新增服务端核对和内容 hash。用户不能通过伪造接口把批注挂到不存在的原文上。

## 流式回复为什么不是收到字就算成功

`apps/web/app/api/discuss/route.ts` 先保存 user 与 pending assistant，再把 SDK delta 转发给浏览器。
收到 completed 才完成落库；失败、中断和用户取消分别处理。页面重开从 messages 表读回真实历史，不依赖当前组件是否还在。
本地 SDK 已使用 store:false/stream:true，并自行携带上下文，符合这条授权路线的限制。

## 为什么凭证不放 SQLite

阅读资料需要可导出，OAuth 凭证需要操作系统保护，两者生命周期不同。auth/ 只保存 DPAPI 加密状态，JSON 备份永远不打包它。
官方 SDK 负责 OAuth、身份验证、刷新与 Responses 协议，GBook 负责 Windows 加密适配、本机会话和产品流程。

## 为什么备份恢复生成新 ID

直接复用 ID 可能撞到现有书籍、批注或消息。恢复先生成映射，再在同一事务写入引用关系；任何原文校验或关系失败都会整体回滚。
原书库不被覆盖，批注时间、消息状态和书签关系会随副本恢复。恢复出的 pending 消息改为 interrupted，不会自动重新调用模型。

## 为什么解析 EPUB 不等于显示网页

EPUB 是 ZIP 中的 XML/XHTML。导入器按照 OPF spine 顺序取正文文字，跳过脚本、样式和头部，不执行网页或访问书中链接。
ZIP 路径、条目数、声明大小和解压总量都受限制；不支持 DRM 与实体声明。这样获得可稳定划线的文字，但不承诺原版字体与插图布局。
